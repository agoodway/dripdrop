## Why

DripDrop ships flexible primitives for lifecycle and transactional sequences (onboarding, nurtures, win-backs, multi-channel trial flows) but the current dispatch model has a known gap for **cold outbound** campaigns: the existing weighted rotation re-rolls per `step_execution_id`, so a multi-step sequence can send each step from a different mailbox — fine for lifecycle, but it breaks RFC threading (`Message-ID`/`In-Reply-To`/`References`) and sender-reputation continuity that cold drip relies on. Hosts also lack the per-mailbox health state machine, ramp-up curves, sender-pool concept, blast-radius sub-caps, and host-callable inbound-reply ingestion that 2025–2026 cold platforms (Instantly, Lemlist, Smartlead, Saleshandy) treat as table stakes. This change adds an explicit `:outbound` mode that turns those primitives on without disturbing the lifecycle code path.

The library should remain flexible enough for any messaging campaign type. Outbound mode is purely additive — lifecycle dispatch, rotation semantics, and FSM transitions are unchanged. No design choice in this proposal makes lifecycle worse to accommodate cold; lifecycle adapters simply ignore the new fields.

## What Changes

- **Sequence-version mode flag**: `sequence_versions.mode :: lifecycle | outbound` (default `lifecycle`). Flips on the new dispatcher gates and changes adapter-resolution behavior. Versioned (per `sequence_version`, not per parent `sequence`) so a sequence can transition between modes by activating a new version. Enrollment snapshots the effective mode at creation time so in-flight enrollments are not affected by mid-stream version changes.
- **Adapter pools as first-class entities**: a new `adapter_pools` table plus `adapter_pool_members` join. A pool nominates a set of adapters with weights and a `class` discriminator (`mailbox_oauth_smtp`, `esp_api`, `smtp_relay`). Pools are tenant-scoped by default. Lifecycle sequences continue to use `is_default` and explicit `channel_adapter_id` selection; outbound sequences reference a pool through `sequence_versions.config["pool_id"]`.
- **Enrollment-time adapter pinning** (outbound mode only): when a sequence is in outbound mode, the dispatcher selects ONE pool member at first dispatch using a Weighted Deficit Round Robin allocator over per-(adapter, sequence) deficit counters, persists it to `enrollments.adapter_id`, and uses that adapter for every subsequent step in that enrollment. Replies thread back to the same mailbox; per-step rotation is intentionally NOT used in outbound mode. An optional `steps.adapter_override_id` lets advanced playbooks (multi-persona sequences) opt into a single-step sender override that explicitly breaks the thread chain.
- **Adapter health state machine**: `channel_adapters` gains `health_state` (`active | resting | probing | ramping`), `health_score`, `resting_until`, `last_send_at`. The existing `BounceComplaintThresholds` writer is extended to drive the state machine with exponential backoff on repeat breaches. A probe phase (small fixed daily cap for 24–48h) verifies recovery before returning to full capacity. The foundation patch already wires `paused_until` enforcement; the new state-machine columns generalize that mechanism.
- **Ramp-up curves per adapter**: new columns `daily_cap`, `ramp_started_at`, `ramp_increment`, `ramp_floor` on `channel_adapters`. The dispatcher computes `effective_cap_today(adapter) = min(daily_cap, ramp_floor + days_since_start * ramp_increment)`. Linear ramp only — no curve JSONB; complexity isn't justified. Adapters without a ramp configured are unaffected.
- **Per-(adapter, sequence_version) sub-cap** for blast-radius protection: a new `adapter_sequence_budgets` table holds `weight`, `max_share_pct`, `daily_volume_target`. WDRR deficit counters live in ETS (rebuild on restart; documented as best-effort fairness, not strict continuity). Prevents a single sequence from burning an entire mailbox's daily headroom.
- **Min-gap-between-sends per adapter** (cross-sequence): `channel_adapters.min_gap_seconds`. Dispatcher checks `last_send_at + min_gap_seconds <= now()` before claiming. Lifecycle adapters leave this null and skip the gate.
- **Daily-cap layering for mixed pools**: today's `sender_mailbox`-keyed daily cap stays as the primary check (works perfectly for OAuth pools where adapter ≈ mailbox). Outbound mode adds a parallel `adapter_id`-keyed cap so an ESP-API adapter sharing many `from` addresses can still be capped at the account level. Stricter constraint wins.
- **Threading metadata**: `step_executions` gains `out_message_id` (the RFC 5322 `Message-ID` we generate and stamp into outbound headers — distinct from `provider_message_id`). `message_events` gains `in_reply_to` and `references_list jsonb` for inbound-side header capture. Email channel adapters stamp `In-Reply-To` and `References` from the enrollment's prior outbound step on follow-up sends in outbound mode. Lifecycle does not stamp these unless explicitly opted-in via step config.
- **Host-callable inbound message ingestion**: `DripDrop.ingest_inbound_message/2` for hosts that pump replies from IMAP / Microsoft Graph subscriptions / Gmail API watches outside the existing webhook ingest path. Correlates against stored `out_message_id` (preferred) or falls back to the existing `provider_message_id` lookup. Routes to the configured `OnReply` callback identically to the webhook path.
- **Optional spintax / variable-pack rendering**: a new `DripDrop.Templates.Spintax` engine layered on top of Liquex. Step config opts in via `template_variation: %{enabled: true, seed: ...}`. Deterministic per `(step_execution_id, attempt_window)` so retries render identical content. Off by default everywhere.
- **Public API additions**: `DripDrop.create_adapter_pool/1`, `DripDrop.add_pool_member/2`, `DripDrop.remove_pool_member/2`, `DripDrop.set_adapter_health/2`, `DripDrop.ingest_inbound_message/2`. All are no-ops or unused on lifecycle paths.
- **Telemetry additions**: `[:dripdrop, :dispatch, :adapter_pinned]`, `[:dripdrop, :dispatch, :pool_exhausted]`, `[:dripdrop, :policy, :ramp_cap]`, `[:dripdrop, :policy, :sub_cap]`, `[:dripdrop, :policy, :min_gap]`, `[:dripdrop, :ingest, :inbound_message]`, `[:dripdrop, :health, :state_changed]`.

## Capabilities

### New Capabilities

- `adapter-pools`: Pool entity (name, tenant scope, on-pin-unavailable policy, member class discriminator, member weights), pool authoring API, eviction state machine integration with adapter health, default-vs-pool selection coexistence, and the WDRR allocator that drives enrollment-time pinning.

### Modified Capabilities

- `channel-adapters`: New nullable columns for health state machine (`health_state`, `health_score`, `resting_until`, `last_send_at`) and ramp configuration (`daily_cap`, `ramp_started_at`, `ramp_increment`, `ramp_floor`, `min_gap_seconds`). Existing `is_default` selection remains unchanged for lifecycle. Outbound mode bypasses `is_default` entirely in favor of pool resolution.
- `enrollment-lifecycle`: New `enrollments.adapter_id` column populated at enrollment time when the sequence is in outbound mode. Lifecycle enrollments leave it `NULL`. New `enrollments.effective_mode` column snapshotting the sequence_version mode at creation time (so mid-flight version flips don't disturb in-progress enrollments).
- `sequence-authoring`: New `sequence_versions.mode` column and corresponding validation. New optional `sequence_versions.config["pool_id"]` referencing an adapter pool. Optional `steps.adapter_override_id` for single-step sender overrides (advanced multi-persona use case).
- `dispatch-execution`: New gates conditional on `enrollment.effective_mode == :outbound`: ramp-cap check, sub-cap check, min-gap check, `out_message_id` generation and threading-header stamping. Adapter resolution branches on mode: lifecycle uses existing `select/3`, outbound resolves through pool → enrollment pin. **No FSM changes** — same `scheduled → claiming → sending → sent | failed | skipped | cancelled` lattice.
- `messaging-policy`: Per-(adapter, sequence_version) sub-cap as a new policy gate (separate from the existing rate-limit and daily-cap gates). Daily-cap gains parallel `adapter_id` keying alongside the existing `sender_mailbox` keying; stricter constraint wins. Min-gap-between-sends as a new gate that runs after concurrency check and before the daily cap.
- `event-ingestion`: New host-callable `DripDrop.ingest_inbound_message/2` API. New `out_message_id`, `in_reply_to`, `references_list` columns wired into the existing normalize-then-persist pipeline. Reply correlation prefers `out_message_id` matching when available, falls back to `provider_message_id` for webhook-fed events that don't carry RFC headers.
- `templates`: Optional spintax/variable-pack rendering layer with deterministic per-execution seeding. Layered on top of existing Liquex/EEx/MJML pipeline. Off by default.

## Impact

- **Code**: New module `DripDrop.AdapterPools` with the pool authoring API and WDRR allocator. New `DripDrop.AdapterHealth` module owning the state machine and replacing the half-implemented `paused_until`-only signal that the foundation patch wires up. New `DripDrop.Inbound` module with `ingest_inbound_message/2` and threading-correlation logic. New `DripDrop.Policy.AdapterPause` (added by the foundation patch), `DripDrop.Policy.SubCap`, `DripDrop.Policy.MinGap`, `DripDrop.Policy.RampCap`. New `DripDrop.Templates.Spintax` rendering layer. Email channel adapters (`Channels.Email.{Mailgun, SendGrid, Postmark, MailerSend, Ses, Smtp, Gmail, Ms365}`) gain `Message-ID` generation and `In-Reply-To`/`References` stamping when called in outbound mode.
- **APIs**: `DripDrop.create_adapter_pool/1`, `DripDrop.add_pool_member/2`, `DripDrop.remove_pool_member/2`, `DripDrop.set_adapter_health/2`, `DripDrop.ingest_inbound_message/2`. Existing public API is unchanged.
- **Database**: New tables `adapter_pools` and `adapter_pool_members` and `adapter_sequence_budgets`. New columns on `channel_adapters` (8), `enrollments` (2), `sequence_versions` (1), `steps` (1), `step_executions` (1), `message_events` (2). All new columns are nullable; lifecycle behavior unchanged when columns are unset. Because DripDrop is not in production yet, these schema additions are folded into the initial EctoEvolver `V01` SQL instead of creating a separate upgrade version.
- **Dependencies**: No new hard deps. Threading-header generation uses already-loaded `:crypto`. Spintax is a small in-house parser, no new dep. Optional dep `:bypass` already exists for tests.
- **Configuration**: New `config :dripdrop, :outbound_defaults` map for tenant-overridable defaults (default `daily_cap`, default `ramp_increment`, default `min_gap_seconds`, etc.). New `config :dripdrop, :adapter_pools, allocator: :wdrr` (only allocator shipping initially; pluggable for future).
- **Operational**: WDRR deficit counters live in ETS — restart resets fairness state, documented as a non-goal for strict cross-restart continuity. Dispatch hot path gains 3–4 conditional gates, all `O(1)` against indexed columns. Inbound poller is the host's responsibility; DripDrop only exposes the ingestion API.
- **Host-app responsibilities**: hosts running cold-outbound sequences must wire an inbound mail source (IMAP, Microsoft Graph subscriptions, Gmail API watches) to `DripDrop.ingest_inbound_message/2`. DripDrop does NOT ship a poller. Hosts must publish `Message-ID`-aligned domains and configure custom tracking domains where applicable. Warmup networks and external reputation integrations (Postmaster Tools, GlockApps seed tests) are out of scope; hosts can feed seed-test scores to `DripDrop.set_adapter_health/2` if they integrate with one.
- **Out of scope for this change**: warmup networks (reciprocal-engagement graphs); IMAP/Graph polling infrastructure; OAuth flows for inbound mail authentication; Postmaster Tools polling; AI-generated first-line personalization (host-side concern, can be pre-rendered via existing template variables); list verification (Zerobounce/NeverBounce integration); CRM sync; warmup-versus-campaign send-volume separation (since no warmup ships here, the question doesn't arise).
